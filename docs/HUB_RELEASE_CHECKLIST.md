# Hub release checklist

Steel's standing rule (25/09/26): every change to the Hub also reviews the security roles and the Hub training. A wave is not done until all of these are ticked.

## Access and roles
- Every new page is enrolled for the right roles (`WA_NAV.register` gate, `wa40Allowed` wrappers for people with their own tab list) and hidden from the ones that should not see it.
- Access profiles (wave127): add the new page to every profile in `hub_access_profiles.pages` with a decision (`all`, `lead` or `none`), and give it a label and a group in both `parts127/a_head.js` and `parts131/a_head.js` (`LABEL`, `GROUPS`, and `LOCK` if the database enforces it), plus its name in `TAB_LABEL` in `src/110_wave110.seg` so Request more access can offer it. Since wave134 the `GROUPS` are the menu's groups; put the page in the same group as in `WA_NAV.layout`. Until then People and access > Profiles lists it under the pages to decide and it follows its built-in gate. Log the decision in the audit trail (`access_profile`, `pages`).
- If the new page shows data that a profile should not read, lock it in the database with `wa_page_ok('<page>')` (as the finance tables and `can_see_board()` do), not only in the menu.
- The profile cards (the "can do" lines) and the "Always true" notes still describe what each profile gives; update them when a flow changes who can do what (wave133 added "Rearrange the org chart" to the Executive and Admin profiles).
- Changes that only some profiles may make go through checked functions with the check inside (as `wa_org_editor()` does for the org chart, and `info_decide()` for passwords), never through direct table writes.
- New tables have RLS that matches the page access (staff, board viewers, own rows), checked with a real account where possible (simulated JWT in a rolled-back transaction).
- A column that must never reach the browser (a password, a token) is left out of the column grants and served only by a checked function that logs each read (as `info_links.secret` and `info_secret()` since wave134).
- A new column that hides rows (the bank's `banked_at`): the web app is covered by a restrictive read policy, but edge functions read with the service key and need the same filter; list every `svc.from(...)` read of the table.
- Board viewers: read-only unless the feature says otherwise, and never confidential operational items.
- Run the Supabase security advisor after the database changes: no ERROR findings. Policies never trust `user_metadata` (anyone can edit their own), views run with the reader's rights (`security_invoker`) and carry no write grants, and new functions are not executable by `anon` unless a signed-out page needs them.

## Structure (since the wave134 audit)
- **Edit the sources, never the build.** Segments in `build/src/` or a parts folder, assembled by its `assemble.py`; `build.sh` runs `check_remaps.py`, which fails on a legacy colour or an old team label. A new segment goes in `MANIFEST.txt` after `134_wave134` and before `110_wave110`, with a `#` note if its position matters.
- **Menu position:** add the page id to its group in `WA_NAV.layout` (`build/parts134/a_head.js`), and nowhere else. No placement code, no observers on `#tabBar` that move anything (wave163's only watch), and nothing that shapes the menu on a timer after `startApp`: the menu shows once, when the `startApp` chain has run (wave163), and `w163.state().after` stays 0 in `test/w163drive.js`. The page's crumb (`118_wave118` `MAST` or its own header) names the same group, and `window.w134.ok()` stays true in the drive test. An app's page goes in `APPS` (`parts153/a_head.js`), the `apps` group of the layout and wave153's hide rule. The phone sheet (wave163b) reads the menu, so a new page shows there by itself; check it at 390 px.
- **Database:** every new table, view and function, and every column whose meaning is not obvious, gets a `COMMENT` in the same migration: what it holds, who writes it, who may read it (and "use X instead" for anything legacy). Team columns hold the `dept_meta` codes; new id columns get a foreign key and an index; code-like columns get a CHECK. Then regenerate `docs/DATA_MODEL.md` with `python3 build/gen_data_model.py`.
- **Edge functions:** the source and `meta.json` in `fn/<name>/`, deployed with `build/fn.py`. AI calls only through the `llm` router (`x-wa-task` with a route in `ai_routes`, `x-wa-caller` with the function name), never `api.anthropic.com`. Team lists carry all seven codes (read `dept_meta` where possible). Anything that deletes, posts or searches widely checks admin or leader inside, not only the staff email domain. The header says purpose, trigger, auth, actions, tables and side effects; add the function to `docs/EDGE_FUNCTIONS.md`.
- **Slack and email:** no new automated Slack post, DM or email without Steel's explicit OK, and none from a test.
- **Who reads a meeting (wave165).** Visibility levels: none or `department` (everyone), `leadership`, `private` (picked people plus leaders and admins) and `speakers` (a one-on-one: only the people in `allowed_people`, no admin, leader or uploader override; `wa_sees_restricted`). The web app reads through row security; an edge function reading with the service key filters itself: open rows only (`visibility.is.null,visibility.eq.department`) for anything many people see (Slack posts, digests, agendas, shout-outs, profiles, AI suggestions), and a meeting's processing sees open work plus work of its own restricted kind. Anything a restricted meeting writes carries its visibility (tasks, updates, decisions, wins, mentions, task notes, `change_log`), and nothing restricted posts in Slack. `archive_only` meetings are never processed (no tasks, suggestions or ideas); Ask the Hub reads meetings as the asker (`wa_ask_meetings`).
- **Onboarding steps (wave166).** A step that is learned in the Avenue Academy links the module (`onboarding_template.training_id`) or the avenue (`academy_path`) rather than pasting a link, so it ticks itself and the video plays inside the Hub; put new onboarding videos in the Academy (Your first week, or the team's avenue), public on Loom when a new person must watch them before they have an account. A lead's moment is an `hr_setup_template` row with `who = 'lead'` and `due_day`; it shows on the lead's Home. No onboarding text names ClickUp or Keela, and no template carries a password.
- **The onboarding journey (wave167).** New onboarding content goes in the journey's settings (`app_config.onboarding_journey`: a week's photo, title, goals, why and lesson) or in the four lessons (edit `build/data/wa167_journey.py`, run it, apply the SQL); photos come from the Photo library's ready ones (no close-ups of the people we serve), numbers from the Hub's key facts.
- **Photos on events and forms (wave168).** A photo shown on an event, a form or the website is a Photo library photo marked ready (team, volunteers, food; no close-ups of the people we serve); a photo from an earlier edition says so ("The 2025 edition"). Posters and photos come from the Hub's own storage only (`OWN` checks). A new public page or card keeps the brand: the green, the lockup, the E that moves, a gold doodle, Barlow Condensed headings. The website stays free of inline style (CSP): crops are classes, not style attributes.
- **Onboarding content and assigned trainings (wave169).** What a week of the onboarding shows people is edited in the HR centre (Edit what people see), never by writing `app_config.onboarding_journey` by hand; a step learned in the Academy links its module or avenue in the step's editor (Done in the Avenue Academy). Trainings for many people go through `academy_assign` (the HR centre or the Academy's Assign), not rows written into `training_progress`, so people see them under Assigned to you with the due date and the note, and HR sees the progress. A new HR-centre or Academy feature checks `wa169_can_assign` (HR's profile, leaders, admins) in the database as well as on the page.
- **Someone's own mailbox (wave170).** Only the owner reads their `mybox_mail` rows and their settings; the function never sends an email (a reply is a Gmail draft the owner sends), never deletes, and writes no subject or sender anywhere another person reads (change_log gets counts and ids), unless the owner sends the email to a team. Personal mail is left alone before a model reads it and kept as its id alone; an owner's voice (their drafting guide) lives in their row only, never in the repo or a migration. Tests use made-up mail and a caught `mybox` function; a real sort is the owner's (or run with them). Since wave201 an owner reads and edits their guide in Your inbox, Settings (the function's `voice` and `settings {voice}`), and a saved draft is read back from Gmail before the Hub says so.
- **Speak instead of typing (wave201).** A new box where people tell the Hub's AI what to do gets the shared mic: add its selector to `TARGETS` in `build/parts201/a_mic.js` (an attribute in `key` when one page draws several), and check it in `test/w201drive.js` (the mic inside or beside the box, words landing, the box found again after a redraw). Never record or send audio from the Hub: the browser's own SpeechRecognition turns speech into text.
- **info@ and emails sent on to a team (wave170).** They are passed on automatically (Steel's choice, 29/09/26): the person it is for gets a Slack DM, else the team's channel; nobody when someone on the team is already on the email. Test with `mail-pull` `test` (`to` info@, `dry_run`) and team-inbox `jev_dry`; a test row (`gmail_id` test-) never reaches Slack. Security mail is never filed or passed on.
- **Announcements (wave180).** Each new announcement posts once in Slack and is emailed once to the people it is for (Steel's choices, 30/09/26); a test never inserts one with `post_slack` or `post_email` on (use team-inbox `announce_dry` with `{draft}`, which only reads and sends nothing). A person's answers are read through `wa180_results` only; keep names out of anything shown for an anonymous one, and text answers away from the people who answered.
- **The Loop (wave192).** Starting a session posts nothing; a wrap-up note goes where the person chooses (their team's channel, the Loop channel or just the Hub) and carries what moved, never a clock time, hours or a private task's title. Session rows (`hub_checkins`, so hours) are read by the person, admins and HR only (`wa169_can_assign`); anything else reads `loop_feed()` and `loop_in_now()`. A draft is built on demand from the person's own records (`loop_trail`) and never stored; no click or page tracking. change_log lines about sessions carry no hours. Test a close with `dry: true`.
- **Updated since you finished (wave194).** A step HR changes after someone finished their onboarding asks them to open it (its module, its avenue or the step in their plan) before they can close it: no Got it. Opening is saved per version of the step (`onboarding_update_opens`) and Close writes `onboarding_update_acks`. A wording-only change keeps the step's `updated_at` (wave190's rule), so people are asked again only when the step really changed. A new place that lists changed steps uses `w194.pendingHtml` or `w194.actsHtml`.
- **Finance is not Fundraising (wave164).** The seven team codes are the teams with pages (`WA_TEAMS.order`); `finance` is a code of its own with no team page, for Finance's tasks, requests and emails (`WA_TEAMS.inbox` = the seven plus `finance`, and a function's team list that files or routes work includes it). Money work (invoices, receipts, payments, reimbursements, purchase approvals, budgets, the books) goes to `finance` and `#accounting-finance`, never to `fundraising`; Fundraising is grants, donors, sponsors and events. Inside an app the rail is the menu: no in-page tab strip or crumb that repeats it on a computer.
- **The serving page's stages (wave191).** A new card on a serving goes into its stage (Plan, Recruit, Confirm, Prepare, Day of, Wrap up: `adoptRail` in `build/parts191/c_event.js`), not a new column or rail; a new SOP step gets its `stage`, and a `hub_signal` when the Hub can tell it is done. A part in a parts folder never declares a top-level function or variable another part of that folder already has (they share one scope: the later one silently wins).
- **Texts to volunteers (wave191e).** Every text goes through `quo_messages` (queued) and quo-send's drain: only between 9 am and 7 pm Montreal (`wa191_sms_window()`), automatic kinds only as `sms_mode` allows, STOP always respected. Never call Quo directly from a new function, never send a text outside the window, and an invitation (`detail.source` recruit) is not a sign-up. A volunteer's text "waits" only until a person answers it (wave191i: a reply in the Hub, Text volunteers, or the Quo app copied in by `sync_threads`); a new way of handling one sets `quo_messages.handled` (answered, done, confirmed, declined) rather than adding its own waiting count.
- **The drivers' run (wave191m).** Driver and team leader times come from the stored run (`volunteer_event_runs`, worked out by serving-run), read through `wa191_run_get` (the Hub) and `wa191_run_for` / `wa174_times` (the volunteer's page); never work out a start time in the page. Map data is OpenStreetMap only (Photon, Nominatim at 1 request a second with the Hub's User-Agent, OSRM), cached in `geo_cache`. A new kind of stop goes into `wa191_run_inputs` and serving-run together, and the run's minutes and addresses live in the Text settings (`volunteer_itinerary_settings`).
- **The storage check (wave191n).** The team leader's own link is the key (as for the survey), one check per serving (the latest answer). A note the check writes in the Inventory says so, and only those notes are cleared by a later check: never a note the team typed. Test links save nothing.
- **Collaborations (wave191o).** Our team leader and community lead are always ours: a partner never covers those roles. A partner's people join through their form (`volunteer_partner_join`: one record with the CRM, tagged with the partner, Confirmed on the serving); the coordinator route keeps a headcount per role instead. Both count toward the roles (`partnerTargets` in `build/parts191/h_partner.js`, read by Plan the roster through `WA191TARGETS`, and the team board).
- **Servings in the onboarding (wave191p).** Every member volunteers four times a year, counted by the fiscal year (October to September). A sign-up from the onboarding is Confirmed right away and reaches Operations Montreal as a Request (`serving-signup`, assigned to the operations lead from the org chart), announced the way every new Request is (the team's channel and the person assigned); nothing is texted to the member.

- **The HR centre's pages (wave197).** A new HR-centre section belongs to one page: tag it in `tagAll()` (`build/parts197/d_router.js`, `data-w197s="<page>"`, block-level sections with `w197blk`), or it stays hidden (anything untagged in `#w46body` is). A new page is a `PAGES` row in `build/parts197/a_head.js` (key, label, rail icon, group, the older tab whose data it needs, its line). Nothing is drawn under every page. In every app the title is the page's name: a page's masthead never repeats the app's name, and an app's quick action belongs in `APPS[...].actions` (wave197 moves it into the header on a computer).

- **French (wave198).** New interface words need nothing: French readers report them and i18n-translate translates them overnight (only words that are in the build). A page that compares its own text with an English string and rewrites it must accept the French too (`window.w198.same(text, en)`), or the two take turns. Text people type must never be added to `hub_i18n`. A new table of onboarding or Academy content joins `hub_i18n_content`'s check, `wa198_content`, `wa198_content_stale` and `CT` in `build/parts198/c_data.js`. Wrap user-typed content that could look like interface words in `data-w198skip` if it must never be translated.

- **Positions (wave199).** A position is a folder in the HR drive, not a row you make by hand: create it from Positions > New position (jd-drive makes the folder) or make the folder in Drive and Sync. Never write CVs anywhere jd-drive's privacy check would refuse.

- **Designed emails (wave202).** A new designed email for volunteers or donors (a welcome, a call-out, a thank-you, an appeal) is a studio template (`crm_email_templates` with `design`; `html_body` from `MAIL202.render`, inline styles on every tag), written through `email_studio_save` and sent by mail-send like any template; not a second renderer or hand-written email HTML (the system templates, receipts and itineraries stay mail-send's own). A new block type goes into `MAIL202` (render, text, `texts`, `links`, `images`) in `build/parts202/c_blocks.js`, the AI's `BLOCK_PROPS`, the editor's `blockForm` and the checks, and `w202drive` checks it. The studio's AI only through the `email_studio` route; its facts rule stays (nothing invented; the writer's words, the template's and the website's public figures), and the page, not the model, works out weekdays. A starter uses only those figures and Photo library photos marked ready. One-offs and templates with [brackets] never reach a picker that sends on its own (`window.w202.sendable`). Voices (wave203): the house voice lives in app_config `mail_voice_wa` (admins edit it in the studio's Voices panel, never in code); a person's own voice is their writing guide from Your inbox, read through mybox's `voice` action and never copied into an email, a migration or the repo. Content first (wave204): the studio's AI works from the writer's content and never stands in for it (40 words of their own before Tell the Hub, every detail before the Hub fills a template, no prompt that pads thin input), and every button that calls the AI says what it costs (about 2¢; `design.ai` keeps each email's spend, `email_studio_costs()` the studio's). A change that makes the studio call the AI more often, or that lets it write from nothing, needs Steel's yes. Video never goes inside an email: a moving preview (an animated GIF made in the browser) links to it.

- **Goals and live editing (wave205).** The organizational goals are the only goal tier (department goals are retired: kept, archived, `retired_at`, out of every default view). A goal's fields, milestones, paths and owners change only through the `strategy_*` functions, whose checks are inside (`wa205_can_edit`: the goal's owners and admins; `wa205_can_comment`: staff but not viewers or blocked people; board viewers read only); never write `goals`, `goal_milestones`, `goal_paths` or `goal_owners` directly. Every change lands in `goal_history` by the trigger `wa205_hist()`, so a new editable field joins the trigger's field list, `strategy_save`'s list and `strategy_restore`. Autosave sends the value the page started from (`p_old`), and a conflict is shown, never overwritten silently. Realtime (`supabase_realtime`: goals, goal_milestones, goal_paths, goal_owners, goal_comments, projects) carries saves to everyone on the page; row security applies per reader, so a table added to the publication needs its read policy first. Projects link to an org goal and, ideally, a milestone through `strategy_link_project` (the sheet is `window.w205.open({kind:'link', ...})`). A document everyone should read goes into the Strategy Library (`strategy_docs`, `pinned`), added by admins. Typed goal content carries `data-w198skip`. `goal-sync` (ClickUp) is paused: turning it back on would add department goals again.

- **Opening a task (wave206).** A task shown anywhere in the Hub opens in the team pages' drawer, `window.w116Board.open(id)` (wave116b, with what 116t, 116m, 132 and 138 add to it); never a second task view. The drawer reads `DB_TASKS`, so a page that lists tasks from its own query puts the fresh row there first (as `w206.open` does on the project page), and repaints itself after a change in the drawer.

## Hub training
- Every new page has a page tour (`w122.tours.<key>`) that walks through each section, and a `trainings` row `tour:<key>` in "Hub page tours".
- Changed pages: the existing tour still highlights every step (`node test/tour1.js all`).
- A menu change: the menu step of the chrome tour names the groups as `WA_NAV.layout` does.
- Lessons or SOPs that describe the changed flow are updated (training 42 for Requests, Hub module 9 for access, and so on).
- **Write trainings to be read (wave190).** A reading starts with `Goal:` (the lead), then short sections under `## ` headings, paragraphs of a few sentences, lists with `- ` or `1. ` (a `- ` line under a `1. ` line is its point), and ends with `Try it:` and `Done when:`; `Tip:`, `Good to know:` and `Watch out:` make a callout. When a wave adds a sentence to a Hub module, put it in the section it belongs to (or a new one) instead of lengthening a paragraph. An onboarding step says what and why in a sentence or two, then `**To complete this step:** ...` (the gold box), then, for a step done in the Academy, `*This step ticks itself when ...*` (the quiet note). No ClickUp or Keela in onboarding text, the Hub is `hub.welfareavenue.com`, and a wording-only change to the master keeps the steps' `updated_at` (as `wa190_reading_pass` does), so people who finished are not asked to re-read wording.
- **Certificates (wave194).** A certificate is drawn by `w194.certHtml` in the brand (the green band with the lockup, Barlow Condensed and Space Grotesk, the gold seal and one doodle) and carries the signature in `app_config` `cert_signature` (name, title, the picture): only admins change it (from a certificate, Signature; the database refuses anyone else, `wa_app_config_guard`, `cert_*`). Never commit the signature's picture to the repo. Check a new certificate on a computer, a phone and in print (one A4 landscape page).
