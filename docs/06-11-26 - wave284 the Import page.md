# wave284: the Import page (built 06/11/26, not released)

Hub CRM slice 1, Phase 4 (design CRM-S1 v2, items 23 to 28; B.1). Built on 06/11/26 on branch `crm-slice1-280-284`, on top of wave281 (the CRM rules) and wave283 (the CRM page and gift rights), both built and not released. Nothing is live. Release waits for Steel's yes, and wave281 and wave283 go first.

## What changes for staff

Admins get an Imports page in the CRM (`#crm/settings/imports`, in the rail after Sources). Nothing changes for anyone else: the item is hidden, the page says "Imports are for admins.", and the database refuses them.

On the page:
- **Runs.** One run at a time, with a picker for earlier runs and New run (a name, then Start a new run).
- **Files.** Pick the kind (Keela contacts and companies, export 15; form responses, export 12; interactions; transactions), choose the file, Upload and stage. The file goes to the private `imports` bucket and is staged 5,000 rows a call, with its progress shown. Keys lists every key or column header with how many rows have a value, never a value. For the contacts file, a select picks the subscription history key (opt-outs and consent read it).
- **Eight cards, in the B.1 order:** opt-outs, Keela fields already in the Hub, people, job title and other fields, organisations, consent history, tags and Campaigns, form answers. Each shows its status as a dot and a word (new, compared, applied, undone, failed), what it does, the report's counts in a sentence ("If applied: Read 1,510 rows; 1,457 matched; 31 new; 52 changes (city 40, phones 12); the Hub kept its own value 3 times."), See the lists, and one button: Compare, Apply or Undo. Opt-outs and consent never show Undo. A card that needs a file says so until it is staged. A stop is shown in the card ("Stopped: missing key Birth Date").
- **Apply and Undo** open a centred confirmation that repeats the counts. Nothing else pops up.
- **Settings in the cards:** organisations has a tick for each close pair (same organisation or not); Keela fields has a select for each Keela assignee (who they are in the Hub); tags and Campaigns has a type for each campaign to create. A changed setting asks for a new compare before Apply.
- **Purge this run** deletes the staged rows, the uploaded files and the change records. It asks inside its own row. 30 days after the last applied batch the card reminds you.

## The rule for Claude sessions

**Claude sessions never query `import_stage`.** It holds Keela's raw rows (names, emails, phones, addresses, birth dates). Read the batch reports (`crm_import_batches.report`), the counts from `wa284_keys`, or ask Steel. A report never holds an email, phone, address, birth date or note: only counts, Keela ids, Hub ids, staff names, organisation names and Keela option labels.

## What it changes

**Database** (`build/data/wa284_import.sql`, needs wave281; it stops at the top without it; it changes no live function):
1. The private bucket `imports` (100 MB a file, JSON and CSV), with insert, select and delete storage policies for `wa_can('import_admin')`.
2. The schema `import_stage` (no grants to anyone, row security on): `import_stage.files` (run, path in the bucket, kind, rows, staged so far) and `import_stage.rows` (one jsonb per row, numbered from 1).
3. `crm_import_runs` (with `purged_at` beside the brief's columns), `crm_import_batches` (one per kind per run; status new, compared, applied, undone or failed; the report; the error) and `crm_import_changes` (every change an applied batch made, in order; a birth date is stored as "set", never the value). Admins read them; nobody writes them but the functions. Every table and column has a comment.
4. The mapping settings (app_config, `keela_` keys, which only admins may change since wave281): `keela_assignee_map` `{}`, `keela_org_pairs_ok` `[]`, `keela_company_category_map` `{}`, `keela_status_map` (To contact and Developing are prospect, Established relationship is active), `keela_tag_map` (as the design's table), `keela_keys` `{}` and `keela_campaign_types` `{}`.
5. The `wa284_*` functions, every one for the service role only (anon and authenticated can run none):
   - `wa284_new_run`, `wa284_register`, `wa284_stage_rows`, `wa284_files`, `wa284_keys`, `wa284_new_batch` (the helpers crm-import calls, since the API cannot reach `import_stage`);
   - `wa284_compare`: runs the batch's writer inside an exception block with the same settings as Apply, builds the report from its change records, then raises `WA284` so everything rolls back; the handler stores the report. Any other stop sets status failed with a message that names a key, a row number or the database's error code, never a value;
   - `wa284_apply`: one transaction with `wa.no_automations` on, `wa.import_batch` the batch and `wa.consent_source` "Keela import"; the writer; the guard; status applied and the run's `last_applied_at`;
   - `wa284_undo`: refuses opt-outs and consent; walks the changes backwards, puts back an update whose column still holds the new value and lists the rest (changed since, kept); never puts back a consent or opt-out column; lists new contacts, organisations and campaigns for review (never deletes them); removes a row it added (custom field, Campaign part, chapter, timeline item, organisation link) only when it is unchanged; removes a birth-date row only when its source and time are still the import's;
   - `wa284_purge`: deletes the run's staged rows, file records and change records, marks the run purged and returns the storage paths;
   - `wa284_fail` (crm-import records a stopped apply), `wa284_guard`, and the eight writers `wa284_w_optouts` ... `wa284_w_form_answers` with their helpers.
6. The side-effect guard: `trg_wa284_import_guard` (before insert) on `dept_requests`, `crm_email_sends`, `quo_messages`, `whatsapp_messages`, `crm_automation_runs`, `hub_notifications_sent`, `volunteer_applications`, `crm_form_submissions` and `event_roster` refuses any row while `wa.import_batch` is set ("import side effect blocked (<table>)"), even inside a subtransaction; `wa284_guard()` also stops an apply that queued a web call (`net.http_request_queue` rows of this transaction).
7. An index on `crm_contacts` for the Keela id, and one release line in `change_log`.

**The batches, as built** (each writer follows its B.1 rule; the key names come from `wa284_key`):
1. `optouts`: for each Keela person, the email opt-out their history says to honour (`wa284_opt_state`): the latest dated event if it is an unsubscribe, a hard bounce or a spam complaint (**on the same date an opt-out wins over an opt-in**, whichever way the list runs), or **any opt-out whose date cannot be read**, unless the latest dated event is an opt-in that the list's known order (its dated events oldest first or newest first) puts after it. Event words are read opt-out first (`wa284_ev_kind`): cancelled, ended, do not email, suppressed, removed, stop and opted out are unsubscribes, cleaned is a bounce, spam or complaint is a complaint, and only then opted in or subscribed is an opt-in; anything else is "other". On a Hub contact that can still be emailed it sets `email_status` unsubscribed, bounced or **complained** (A.4: not a working address) and `consent_source` "Keela: <event> <date>" or "Keela: unsubscribe (undated)". The report counts the events with no readable date (`undated_events`), the undated opt-outs honoured, and the events whose words the import does not know (`unrecognised_events`, with the words listed in `unrecognised_event_types` for staff to check before applying). Never undone.
2. `legacy_fields` (no upload, from `legacy_refs.keela`): positions split on ", " and mapped to the `volunteer_positions` options by label (or a role guide's label; unmapped ones listed), availability, dates volunteered (a field), Rally Paper team, donor readiness (R, SP, NR), the assignee as `owner_member_id` through `keela_assignee_map` (unmapped ones listed). Fills empty fields only.
3. `people`: by Keela id (`legacy_refs.keela.contact_id` or `keela_extra_ids`), then email, then phone (listed, never merged); new people with an email or phone (source keela); neither: skipped and listed. **A new person starts with the email opt-out their Keela history records** (batch 1 ran before they existed): `email_status` unsubscribed, bounced or complained and `consent_source` "Keela: ...", never undone; the report counts them (`created_not_emailed`). Fills empty names (a full name that is empty or an email counts as empty) and address fields, adds missing phones and emails, appends notes as "From Keela: ...", keeps duplicate Keela ids in `legacy_refs.keela_extra_ids`. The Hub wins. `primary_email` is generated from `emails[1]` on live, so it is never written. It needs the subscription history key too.
4. `fields`: job title; birth date into `crm_contact_private` only (ISO dates only; a person with a private row keeps it; the change record says "set"); car, LinkedIn and food licence custom fields.
5. `orgs`: companies matched to `wa_partners` by `keela_company_id`, then normalised name or aka; exact matches linked; close pairs listed and linked only once ticked (an unticked pair is skipped, not created); a person's name, a phone number or Welfare Avenue skipped and listed by Keela id only; real new ones created (category from the map, else partner, the type listed; status from the map, else the column default past; visibility everyone; goals); people linked through `crm_contact_orgs`.
6. `consent`: every dated event into `crm_consent_events` once (source keela, column "keela email subscription" or "keela sms subscription", the type's words, the form name, the batch); express email consent only when the latest dated email event is an opt-in with a form name (on the same date anything else, an opt-out first of all, beats an opt-in), **there is no email opt-out with an unreadable date**, and the address is not unsubscribed, bounced, complained or do-not-contact. **A Keela text opt-out sets `sms_opt_out`** (the consent log's source "Keela: text opt-out <date>"), unless one of the contact's phones texted START to the Hub after it; a text opt-in becomes `sms_consent` unless texts are stopped or a text opt-out has no readable date. Never undone.
7. `participation`: tags by `keela_tag_map` to Campaign parts (the campaign by `keela_name`, else by name), the Toronto chapter, skip, or `tags[]`; a campaign not in the Hub is created with the type picked on the page, else listed.
8. `form_answers`: responses with no Hub interaction of the same id (source keela, `source_ref` "keela:<id>", the first import's shape) become `crm_interactions` rows (kind form, direction in, channel website, the form name, "Question: answer" lines, the day given), leaving out answers whose question mentions a birth date or DOB, health, a medical matter, medication, a condition, a disability, diet, an injury, allergies or an address; a Toronto form adds the Toronto chapter.

**Checks every batch shares** (review fix round): a contacts file in which no row has a Contact Type of Individual or Company stops the writer with "wa284: no staged row has a Contact Type of Individual or Company" (a different spelling can never make batch 1 read nothing and skip every opt-out in silence; rows of another type are counted as skipped); compare keeps its basis in the report (the staged file's id, rows and time, and a checksum of the settings that batch reads), and Apply refuses with "the staged file or the settings changed since the compare; compare again" when either changed, so what is applied is what was compared; the orgs writer works its name lookups out once (person names, company names, partner names and Keela ids as jsonb maps) instead of rescanning for every company and person.

**Key names.** The writers read the [FIELDS] names by default (Contact Id, Contact Type, Full Name, First Name, Last Name, Primary Email, Primary Phone, Street, Street Line 2, City, Province, Postal Code, Country, Notes, Title, Birth Date, `Car: "Make, Model, Type"`, LinkedIn, Food Licensing Certification, Tags, Companies, Company Type, Status, Goal; for responses Response Id, Form Name, Contact Id, Email, Submitted Date, Answers; inside the subscription history date, type and form_name). Keela's raw JSON may name them differently: before the first compare, open Keys and set any that differ in `app_config.keela_keys` (for example `{"subscription_history": "...", "birth_date": "..."}`; a key set to "" means the export does not have it, and that field is skipped). The subscription history key has no default and is picked on the page. A key no row has stops the writer with "missing key <name>".

**crm-import v1** (`fn/crm-import/index.ts`, `stage.mjs`, `meta.json`; verify_jwt on; built, not deployed). Every action first asks `wa_can('import_admin')` with the caller's own token. Actions: new_run, register, stage, files, keys, batch, compare, apply, undo, purge (see `docs/EDGE_FUNCTIONS.md`). CSV is parsed with `jsr:@std/csv` 1.0.6. Compare, apply and undo run over a direct Postgres connection (the function's built-in `SUPABASE_DB_URL`, deno-postgres v0.17.0 pinned), in one transaction that first runs `set local statement_timeout = '140s'` (the API's authenticator role stops statements after 8 seconds, and the edge function's request ends at 150, so the database stops first and a batch too slow for it rolls back whole; no role is altered); without `SUPABASE_DB_URL` they fall back to the API and the reply carries a note, on success and on error, which the card shows. Errors pass through only when they are the database's own messages (missing key, wa284:, import side effect blocked); anything else becomes its error code.

**The page:** `build/parts284` (new, `284_wave284.seg`, in MANIFEST after `279_wave279`), `build/parts152/c_list.js` (the imports tab from `settings/imports`, `paintImports` draws `#w284root` and calls `window.w284.open`; after the capabilities load, an admin's rail is drawn again so Imports appears), `build/parts153/a_head.js` (the rail item after Sources when `window.w152.can('import_admin')`).

## Worth knowing

- **Key names are confirmed on the page, not assumed.** The design gives the [FIELDS] names, and the subscription history key only once `wa284_keys` shows it. Keela's raw JSON may use other names; `keela_keys` maps them without a code change, and a key no row has stops the writer with "missing key <name>" rather than importing nothing quietly.
- **Additions beside the brief:** `crm_import_runs.purged_at` (so a purged run's batches cannot be undone or re-run and the page knows it); the crm-import action `files` and the function `wa284_files` (the page cannot read `import_stage`); `wa284_fail` (an apply rolls back, so crm-import records the stop afterwards); `app_config.keela_campaign_types` (where the participation card's type picks are kept); the contacts file's subscription history select (it writes `keela_keys.subscription_history`); the lists `phone_only`, `positions_unmapped`, `company_types_unmapped` and `campaigns_created` in the reports; `wa284_compare`, `wa284_apply`, `wa284_undo` and `wa284_new_run` take an optional `p_by` (the admin's email, for `applied_by` and `undone_by`); `crm_contact_orgs` links are removed by undo when unchanged, like the other link rows. The review fix round added `wa284_opt_state`, `wa284_ev_kind`, `wa284_ev_rows`, `wa284_optout_status`, `wa284_optout_words`, `wa284_types` and `wa284_basis`, the report counts `undated_events`, `undated_optouts_honoured` and `created_not_emailed`, and the report's `basis`.
- **Choices where the live schema and the brief differ:** `wa_partners.category` and `status` are not null with defaults, so an unmapped company type takes partner (the type is listed) and a missing status takes past; the design says "left null". `keela_company_category_map` starts empty because Keela's company types are not in the design; fill it after the first compare lists them. "Gift Basket Drive 2026" has no `keela_name`, so a campaign is found by `keela_name`, else by name. An unticked close pair is skipped, not created, so a later tick cannot leave a duplicate.
- **The net-queue check.** Compare runs in a subtransaction, so the `net.http_request_queue` check (which matches this transaction's id) runs only at apply; the nine guarded tables are caught in both. The check sees only the top-level transaction id, so a web call queued inside a trigger's own exception block (a subtransaction) would be missed; nothing on live does that today.
- **Undated events.** Keela's history may hold events whose date the import cannot read (anything but an ISO date). An opt-out among them is honoured (batch 1, and new people in batch 3) unless the latest dated event is an opt-in that the list's order clearly puts after it; with fewer than two dated events the order is unknown, so the opt-out stands. Batch 6 grants no express consent, and no text consent, past one.
- **Size.** Each stage call reads the whole file from storage and sends up to 5,000 rows to the database in one request; the 46,925-row interactions CSV takes 10 calls. No batch reads that file yet: interactions and transactions are staged for the December note (B.6).
- **Tests on this PC:** PGlite and std/csv are installed with `npm install --no-save` (this worktree has no package.json, so installing one package removes the other; install both together). The drive tests use the main repo's Playwright.
