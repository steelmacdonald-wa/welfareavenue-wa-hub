## What it does

- **The schedule**: `wa-loom-pull` wakes at 11:30 and 12:30 UTC on Monday, Wednesday and Friday and calls `loom-pull` only when it is 7 o'clock in Toronto, so the pull runs at 7:30 all year (summer and winter time).
- **The pull** (`loom-pull` `sync`): reads Loom through the Atlassian Rovo MCP server (v2), as `hub@welfareavenue.com`, the Atlassian account that runs the Welfare Avenue Loom workspace (site `welfareavenue-29450069`, cloud id in `loom_cloud_id`) and records the meetings. It lists the recordings created since `loom_pull_since` (2 September 2026, the day after the last meeting filed by hand), owned and shared, oldest first, at most `loom_pull_max` (10) and about 100 seconds per run; the rest wait for the next run. Each new recording's transcript comes as Loom's phrases (speaker, seconds, text) and becomes "MM:SS Name: text" lines, like the uploads. It only ever calls read tools: `readOnlyTool()` refuses any tool with a word in its name that changes something (create, update, share, move, delete and so on).
- **Who sees a filed meeting**:
  - the weekly team meetings (Operations, Toronto Operations, Fundraising, Marketing, Human resources, Program Development) are filed under their team for everyone;
  - leadership meetings: department Leadership meeting, visibility leadership (the leaders, the board circle and the admins), which also starts process-leadership;
  - everything else (one-on-ones, check-ins, interviews, onboarding, working sessions): confidential to the people in it who are on the Hub (the speakers, and the invitees Loom lists as collaborators, matched to the roster by name or email) plus the leaders (Ahmed, Amanda, Kahkashan, Shima today; the admins see everything). The team comes from the title, else from the people in it.
  - Loom's own sharing setting is not used: the meeting recorder keeps every recording to its owner (`OWNER`), team meetings included (checked on the real recordings).
- **What waits for an admin** (needs a look): board meetings; anything whose title or transcript may hold something sensitive (a role changing hands, pay, discipline, legal matters; the reason shown never names which); recordings shared by someone outside the team; meetings whose team is unclear.
- **What is skipped**: one person speaking (a recording, not a meeting; an admin can still file it); no transcript after five days. A recording with no transcript yet waits and is tried again.
- **What is left out**: personal recordings (recovery and the like, from the title or at least two signs in the transcript). Only the id is kept, never the title or anything else, so the Hub never reads them again. The card counts them and nothing more.
- **Nothing is filed twice**: the 52 Loom recordings filed by hand before (54 transcripts; two were filed twice) were recorded as filed, and a recording already in the archive by its Loom link (an upload, or the Hub inbox filing its summary email) is marked, not filed again.
- **The pipeline**: a filed meeting goes through `process-transcript` as any upload does (tasks, updates, decisions, content ideas, mentions), and a leadership meeting through `process-leadership` too. Their Slack posts are **off** for Loom-filed meetings until Steel turns `loom_pull_slack` on (process-transcript v15; process-leadership v3, platform v13, added on 29/09/26 after the check found that a leadership meeting would still have posted its counts note), so a catch-up never floods #exec-dashboard.

## Connecting Loom (the Atlassian side)

- **The API token route does not work for Loom.** An API token for Atlassian MCP V2 (`read:loom:agent-interface`, `read:me`, `read:account`) was made for `hub@welfareavenue.com` and kept as the Edge Function secrets `ATLASSIAN_EMAIL` and `ATLASSIAN_API_TOKEN`, and Steel allowed API tokens in Atlassian Administration, Rovo, Rovo MCP server, Authentication. The key signs in and lists the tools, but every Loom call answers "Cloud id dfa46f34-... isn't explicitly granted by the user", with the cloud id and with the site address (`https://welfareavenue-29450069.atlassian.net`, Atlassian's suggested workaround, which resolves to the same id); `getAccessibleAtlassianResources` answers no sites for it. `loom-pull` keeps the token only as a fallback for when there is no approval (it never falls back once an approval has lapsed).
- **The Hub connects through Atlassian's approval** (wave162c, `loom-connect`, the way Claude's own Atlassian connector does): OAuth 2.1 with PKCE, a public client registered once by dynamic registration (a client metadata document is also served at `/functions/v1/loom-connect/client.json`), the resource `https://mcp.atlassian.com/v2/mcp`, and the scopes `read:loom:agent-interface read:me read:account email offline_access`. On the approval page the admin picks the site `welfareavenue-29450069.atlassian.net`; the only permission shown is Read, `read_loom`. The refresh token lives in the vault (`LOOM_OAUTH_REFRESH`, rotated on use) with a short-lived access token (`LOOM_OAUTH_ACCESS`). With it the Hub's MCP session lists 8 tools, all read-only Loom tools plus the site and user look-ups.
- **The email scope is required (found 29/09/26).** Without `email`, Atlassian shows the approval, then its sign-in step (id.atlassian.com, an Auth0 login under auth.atlassian.com) answers `invalid_request: Incorrect request parameters` after Accept, whatever else the request holds (with and without prompt, resource or an audience; a short state; a registered client, a metadata document or a localhost return; enterprise managed authentication on or off). OpenAI's Codex hit the same wall (openai/codex issue 36026, closed pending Atlassian Support). It was found by asking for every scope the server lists and keeping only `read_loom` on the approval page, which worked, then narrowing: the only difference was `email`. `loom-connect` v2 (platform v7) asks for it, so Connect Loom on the card works as designed.
- The Rovo MCP server's Domains list needs the Hub's address: `https://zwnmulmnvopclzcvytce.supabase.co/**` (patterns need `/**` for a path). Steel also added the exact function address, the bare origin and `http://localhost:*/**` while the cause was being found; none of those are needed (localhost is one of Atlassian's supported domains anyway).
- Set-up only (trigger secret): `start` takes a `variant` (scope, prompt, resource, audience, a metadata-document client, or `local` for a client that returns to `http://localhost:53682/callback`), and `finish` completes an approval from a pasted localhost address. `build/loom_connect_try.py` prints a link for a variant; `build/loom_connect_call.py` calls status, start, disconnect or finish.
