# wave295: filters on the Contacts page (built 07/11/26, fix rounds 1 to 3 09/11/26, not released)

Hub CRM, Contacts filters and Keela data (design `05 Contacts filters and Keela data - design.md`, "Wave 295"). Steel, 07/11/26: the CRM had "a lack of capabilities in terms of filtering to find people with different fields in their contacts". Built on 07/11/26 on branch `crm-filters-294-295` (worktree `hub-repo-crm2`), cut from the live state (live page `ffb1d928`, live SQL at c157e49). Nothing is live. Release waits for Steel's yes, and wave294 goes first.

## What changes for people

- **A Filters button on the Contacts page**, beside the menus that are there today (type chips, volunteer role, activity, email permission, sort and search stay exactly as they are). It opens a panel of conditions: *field · condition · value*, "Add a condition", and "Or another group". A person shows when they match every condition in a group; with two groups or more, matching any one group is enough.
- **What you can filter by**: Contact type, Volunteer role, Tag, Chapter, Email permission, Email address, Phone number, Served at an event, Gave a gift, City, Language, Came from, Added to the CRM, Last activity, Opened a Hub email, Clicked a Hub email, Organisation, Job title, Do not contact, Volunteer record needs a review, and **every custom field by its label** (under "Keela and profile fields": Rally Paper team, Donor readiness, Instagram, age 16 or older, and any field added later). Each field offers the conditions that fit it: option boxes for a choice, before and after for a date, yes or no, more or less than for a number, contains for text, and "is filled in" or "is empty" for any custom field.
- **Several values at once** for Contact type, Volunteer role and Tag (tick the boxes; a tag can be "has", "has all of" or "does not have").
- **Tags by their Keela names.** The tag box lists the Hub's tags with how many people have each. Typing a Keela name shows the Hub tag it became ("volunteer server → server"); the search also finds people by the Keela name.
- **Chapter**: Montreal or Toronto. As elsewhere in the CRM, "No chapter: counted as Montreal."
- **The count as you build**: "142 people match", counted with the menus and search above, and the button says "Show 142 people". Show narrows the list.
- **Chips** under the bar show each condition in words ("Tag has server", "Chapter is Toronto"); the × on a chip removes that condition. "Change" reopens the panel; "Clear filters" removes them all. The Filters button shows how many are on.
- **The address keeps the filter** (`#crm/f/…`), so a reload or a link sent to a colleague opens the same list. While the database answers, the list says "Finding who matches…" instead of showing everyone first.
- **Save as a list** opens the Lists page with these conditions (and the menus and search) in a new list, the name box ready. **Open a saved list** in the panel, or **View in Contacts** on the Lists page, shows a live list's people on the Contacts page; changing the conditions there does not change the list.
- **Nobody matches**: "No one matches. Remove a condition, or clear the filters." **An error**: "The filter did not run: (the reason in plain words). The list has not changed."
- **Lists gain the same conditions**: the Lists page uses the same condition rows, so lists can now use chapters, custom fields, several types or tags, and the rest. A list saved before keeps its exact shape and meaning.
- Phones (390 and 320 px) and 200% zoom: the panel stacks. Keyboard: every control is a real button, box or menu; the panel opens with the focus on its first field, Escape closes it and puts the focus back on Filters, and removing a chip moves the focus to the next one.

## What was built

**Database** (`build/data/wa295_filters.sql`; needs waves 281, 283 and 294, and stops at the top with a plain message without any of them):

1. `crm_contact_match(c, k)`: one block inserted right after the function's `begin`, in place of the live first line `if f is null or f = '' then return true` (exact anchor in the live text, as waves 273, 281 and 283 did; a missing anchor stops the file; skipped when its wave295 text is there). **It fails closed first** (fix round 1): an unknown or missing field, an object value, a list of values anywhere but kind, role, tag and field is/any, a list with no non-blank value (whatever the operator), a blank value on any condition that takes text, and an operator a new field does not take all match no one. Then it answers for the new shapes and returns; every older condition with one non-blank value goes on to the live code unchanged:
   - `field` `{f:"field", key, op: set | empty | is | any | contains | before | after, v}` over `crm_contact_fields`: a list of choices matches any of them, case-insensitive; yes/no takes only a yes word (true, yes, y, 1, oui) or a no word (false, no, n, 0, non) and compares only stored answers that are one of those; dates (YYYY-MM-DD only, so DateStyle never guesses) compare as dates and numbers as numbers (a value that is not a date or number matches nobody, nothing fails); an empty string, an empty list or a JSON null counts as empty. An unknown key matches nobody, whatever the operator.
   - `kind`, `role`, `tag` with a list (or op `any` / `all`): any of them; `all` every one; `not` / `none` none of them. The donor and partner rules of `kind` are kept for each value.
   - `tag` through `crm_tag_aliases()` (wave294): a value matches its Hub tag too. A value that is not a Keela name goes to the older code.
   - `chapter` (montreal counts a contact with no chapter row), `dnc`, `phone` (a blank number does not count), `org` (the Partners link or the volunteer record's organisation; empty text matches no one), `job_title`. `not` / `none` turn these around, as for the older conditions.
2. `crm_list_preview(p_filter)`: the same query, except that **no group, or a group with no condition, matches no one** (live: everyone), with the filter prepared once per query by `crm_filter_prepare` / `crm_filter_prepare_tag` (each tag value gets the names it stands for as `w295sets`), so a Keela name costs nothing per contact. It is replaced only while its text is still the live one (md5 8088527269cf3f6b75105421ee453abf). Lists, Sends (mail-send) and `crm_list_members` call it as before.
3. `crm_filter_contacts(p_filter) returns table(id bigint)`: staff with the CRM only (`is_wa_staff()` and `wa_page_ok('crm')`, else errcode 42501 "Only the Welfare Avenue team, with the CRM in their apps, can filter the contacts."); a filter without `groups` or with no condition is refused (22023); security definer, stable, `crm_list_preview(p_filter)`. The page calls it.
4. Grants: `crm_filter_contacts` to authenticated only (not anon, not PUBLIC, not the service role); the prepare functions and the two changed functions keep authenticated and the service role. The service role's execute on `crm_tag_aliases()` is **wave294's** (3b1d7ca): wave295 no longer grants or revokes it, and stops at the top if it is missing (a Send to a list with a tag condition would otherwise stop with "permission denied"). Comments on every new or changed object; one release line.
5. **The release guard** (reads only, before anything changes): the file stops, naming each list and why and each unsent Send (draft, queued, sending), when a dynamic saved list holds a shape whose answer wave295 changes: an unknown or empty field, a blank value, a list or object value, no group or an empty group, or a tag value that is a Keela name of another Hub tag (review M1: aliases would widen it). On 09/11/26 live had 0 saved lists and 0 Sends.

## Worth knowing

- **Older labels kept.** The design's picker words (Type, Source, Last active, Has email…) were weighed against the labels saved lists already read with ("Contact type is Volunteer and Served at an event in the last 365 days"). The older fields keep their labels, so the Lists page and the older tests read as before; the new fields use the design's words (Chapter, Organisation, Job title, Do not contact, Phone number).
- **Search does not use Keela names yet.** The quick search runs in the page over each contact's tags; only the Filters' Tag condition uses `crm_tag_aliases()`. Adding it to the search box is a small follow-up.
- **The count in the panel is the database's answer intersected with the menus and search**, so it matches the list it will show.
- **A condition waiting for a value** (no box ticked, no date) cannot be shown or saved; the reason shows under the buttons.
- **Keela names and saved lists.** A tag condition also matches through `crm_tag_aliases()`, which reads `app_config.keela_tag_map`. Editing that map (there is no page editor; it is changed by SQL) changes who a saved live tag list holds, and so a Send's audience. Check the Lists page counts after any change to the map.
- **Fail closed everywhere.** Anything the engine does not understand matches no one, in Contacts, Lists and Sends alike; the live engine matched everyone.
- **Not in this wave**: CSV export and bulk tagging of the filtered list (gap review items 8 and 9), on Steel's yes.
